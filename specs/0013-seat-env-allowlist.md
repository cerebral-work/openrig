# 0013-seat-env-allowlist

## Overview

Every OpenRig seat inherited the operator's shell environment. In one seat on 2026-10-18, counted by name only:
- 78 secret-named names;
- `OP_SERVICE_ACCOUNT_TOKEN`, which opens the 1Password service account;
- `KUBECONFIG` pointing at a cluster-admin file.

They reach a seat two ways:
- 22, including `OP_SERVICE_ACCOUNT_TOKEN` and `KUBECONFIG`, are in the tmux server's global environment;
- 56 are exported by the pane shell's own startup file (on the estate, credential references) after tmux has started it.

So a filter on tmux's environment alone cannot keep them out of a seat. This spec extends 0006 with an allow-list mode, off by default, that an operator turns on with a config switch, one pilot rig first if wanted.

## Design

1. Settings (daemon and CLI stores, in lockstep):
   - `seat_env.mode`: `filter`, the default and today's 0006 rule unchanged, or `allowlist`.
   - `seat_env.base`: names and `PREFIX*` patterns a seat keeps.
   - `seat_env.exceptions`: exact secret-named names the operator approves by name. No patterns; a never-list name (below) is refused even if listed.
   - `seat_env.kubeconfig`: default `<OPENRIG_HOME>/seat-env/kubeconfig`. An operator points it at a scoped kubeconfig in its own config.
   - `seat_env.rigs`: pilot rigs; empty means every rig. A session name with no rig, such as a probe, follows the mode.
   - The daemon reads them at each launch, so a change applies to the next one. If they can't be read, launches are refused (`seat_env_refused`, step: resolve the seat env policy) unless filter mode was the last policy read: never a silent fall back to the full environment.
2. The default base list:
   - HOME, USER, LOGNAME, SHELL, PATH, PWD, SHLVL, TERM, COLORTERM, TERM_PROGRAM(_VERSION), TZ, TMPDIR;
   - the locale by name: LANG, LANGUAGE, LC_ALL, LC_COLLATE, LC_CTYPE, LC_MESSAGES, LC_MONETARY, LC_NUMERIC, LC_TIME;
   - the XDG base directories by name: XDG_CONFIG_HOME, XDG_DATA_HOME, XDG_CACHE_HOME, XDG_STATE_HOME, XDG_RUNTIME_DIR, XDG_CONFIG_DIRS, XDG_DATA_DIRS. There is no `LC_*` or `XDG_*` wildcard, which would carry any value under a non-secret name; no runtime here needs `XDG_SESSION_*`;
   - TMUX and TMUX_PANE;
   - OPENRIG_*;
   - SSH_AUTH_SOCK;
   - WSL_INTEROP, WSL_DISTRO_NAME and WSLENV;
   - CLAUDE_CONFIG_DIR and CODEX_HOME.

   The WSL names keep the 1Password signing bridge (`op-ssh-sign-wsl.exe`) usable. They also keep Windows interop reachable from a seat, a known residual tracked in the seat-user plan (G12).
3. What a seat keeps:
   - the base names and the launch's own names, but never a name matching `KEY|TOKEN|SECRET|PASSWORD|CRED|PASSPHRASE|PRIVATE` (any case);
   - except `OPENRIG_ACTIVITY_HOOK_TOKEN`, one named constant: the daemon mints it per seat as that seat's own activity credential, not an inherited operator secret;
   - except names listed in `seat_env.exceptions`;
   - and never a name on the never list, 1Password service-account credentials: `OP_SERVICE_ACCOUNT_TOKEN` and every `OP_SA_*` name. The never list beats the base list (including a pattern such as `OP_*`), named exceptions and the launch's own names, and the config stores refuse it in `seat_env.base` and `seat_env.exceptions`.
4. Layer 1, tmux (`tmux.ts`), on all three 0006 launch paths: fresh `createSession`, `respawnPane`, and the native resume probe.
   - Every global name the seat may not keep, and every launch name that is secret-named, is marked removed for that session.
   - So is every name tmux's `update-environment` option copies from the creating client (by default `DISPLAY`, `KRB5CCNAME`, `SSH_CONNECTION` and the rest of tmux's list) that the seat may not keep. These follow the allow-list; they are not the launch's own. `SSH_AUTH_SOCK` is a base name, so it stays; `KRB5CCNAME`, a Kerberos credential-cache pointer, is dropped unless allow-listed.
   - `KUBECONFIG` is set explicitly, then the fresh pane restarts. A fresh pane that upstream's scoped launch started is not restarted: it starts under `env -i` with its own selection, from a private file the pane removes as it starts, so a restart would re-run that start command with the file gone and the pane would exit at once (seen live on cw.1-rc.2, 2026-10-26). Layer 2 still stages every command the daemon starts in that pane behind the prologue that sets `KUBECONFIG` and removes the names the seat may not keep.
   - The launch logs the count dropped and the secret-named names dropped, names only.
5. Layer 2, every command the daemon starts in a seat pane (`sendShellCommand`, and `sendLaunchCommand` for a launch outside a runtime adapter):
   - The command is always staged as a script. Its first lines, generated by `seatEnvScrubScript`, run in bash, zsh, dash or sh:
     - they list the environment from awk's `ENVIRON` keys, which a multi-line value or an exported function body cannot fool, and which include bash's exported functions (`BASH_FUNC_<name>%%`);
     - a listing that produced nothing refuses (step: `list the environment`). Without awk on the pane's PATH the listing is empty, and a missing tool must never read as an empty, clean environment;
     - they unset every name the seat may not keep (a function with `unset -f`). A name that cannot be unset, a readonly export or a non-identifier name, is tried in a throwaway subshell first, so no shell aborts on it;
     - they list the environment again. If any name the seat may not keep is still there, the script prints `seat_env_refused` with its step and the surviving names, never a value, and exits 126: the command does not run;
     - the loops run with noglob (`set -f`), so a listed name such as `PAT*` can't match a file in the working directory. The shell's own setting is restored before the command;
     - the shell's own names are kept: `_`, `OLDPWD`, gawk's `AWKPATH` and `AWKLIBPATH`, and bash's readonly option flags `SHELLOPTS` and `BASHOPTS` (an rc that exports them would otherwise make every bash launch refuse). None is secret-named. The launch's own names are the session's names except those `update-environment` copied;
     - they export `KUBECONFIG`. Then the command runs.
   - The script runs in the launch's own subshell after the pane shell's startup files, so names those files exported are dropped too, and shell functions such as an rc `claude` still work for adapter launches.
   - A launch through `sendLaunchCommand` (the stub runner and the resume-metadata probe) is one executable, and it replaces the staging shell (`exec`) once the scrub has run. So it is the pane's foreground process, as when typed in filter mode: the stub runtime's readiness check and the resume probe read `pane_current_command`, and a child of the staging subshell reads as a shell (cw.4.3, found in QA). On this path, an rc function or alias with the runtime's name is not used; the executable on `PATH` is. If a host's rc function wraps the runtime to set configuration (for example `CLAUDE_CONFIG_DIR`), set that through `seat_env.base` or the member's env instead. Otherwise the probe tests the token against the bare executable's configuration.
   - The resume probe judges its pane only after its launch has started:
     - Started means Claude's own process (`claude`, or `node` for an npm install, the names the claim service expects for `claude-code`) was seen in the foreground. The scrub's helpers (`awk`, `rm`) don't count.
     - A shell before that is a launch still starting, not a return to the shell.
     - A probe whose launch never starts is inconclusive, and so is one the scrub refused: Claude never ran, so the token was not tested.
     - A refusal is the scrub's own line, `openrig: seat_env_refused (step:` at the start of a pane line, while Claude isn't the foreground process. It is checked after the resumed assessment. So a live Claude whose visible history merely mentions the refusal is still judged on its own state.
     - A token the probe never tested is never reported not resumable. Such a report would make the next restore of that seat start fresh and lose its conversation.
   - Only names and the `KUBECONFIG` path appear in the script; no value is read into it.
   - **Covered:** every runtime adapter's launch and resume (Claude, Codex, Pi, agy, the managed Claude launch), the resume-metadata probe and the stub runtime.
   - **Not covered:**
     - text typed into a program that is already running (prompts, startup files, handover packets, `rig send`);
     - the web terminal and a terminal-runtime seat's interactive shell, which keep what their own startup files export (layer 1 still applies);
     - a shell that reads its startup files again (`bash -l`, `exec bash`, sourcing the rc), which re-exports them by design.
     The Claude adapter's and `claude-resume`'s unwrapped branches run only without `SeatLaunchEnvironment`, which startup always wires.
   - **The guarantee:** the environment of the process each send starts.
6. `KUBECONFIG` is never left unset, because kubectl would then use `~/.kube/config`.
   - It is the scoped file when that exists.
   - Otherwise it is `/nonexistent/openrig-seat-env/kubeconfig`, a path an unprivileged seat can't create, with a launch warning naming the configured file.
   - So the seat inherits no kubeconfig and kubectl never falls back to `~/.kube/config`. Kubeconfig files themselves stay readable by the seat's unix user, so `kubectl --kubeconfig <file>` still works; that is out of scope here (see the seat unix-user plan).
   - The managed Claude launch, which runs Claude under `env -i`, passes the same path explicitly.
7. Fail closed:
   - If the allow-list can't be applied (the environment can't be read or written, or the command can't be staged), the launch is refused with `seat_env_refused`. It never goes ahead unwrapped.
   - A session the refused launch created is removed.
   - **Where a refusal is recorded:**
     - When the daemon can't apply the allow-list (the policy can't be read, the environment can't be read or written, or the command can't be staged), the launch result carries `seat_env_refused` with the step, and the launch reports it.
     - When the scrub refuses inside the pane (no listing, a name that can't be unset, a survivor), the daemon can't see inside the launch's subshell. The refusal goes to the pane's stderr with the step and the surviving names, never a value. The command doesn't run, so the seat fails readiness, which the daemon records.
   - A non-POSIX pane runs the staged script with `/bin/sh`.
8. No launch value in a failure (review r2 on #15):
   - A failed tmux command's error starts with its whole command line, including every `-e NAME=VALUE` launch value, and can carry its output.
   - `classifyWriteError`, the filter-mode warning and every allow-list refusal keep only a code, the tmux step (`tmux new-session failed`), the names (never the values) of the command's `-e` launch variables and, for known phrases such as `duplicate session`, tmux's reason. #15's respawn redaction composes with it.
   - This applies to every transport (exec, argv and control mode share the format) and to both modes.
9. No secret value on a tmux argv (security finding, 2026-10-18):
   - **Why argv matters:**
     - A tmux server keeps the argv of the command that started it, so `ps` and `pgrep -af` show it for the server's whole life.
     - A short-lived tmux client shows its argv while it runs.
     - So a `-e NAME=VALUE` value is readable by anything on the host. The daemon passed the activity-hook token that way, and a `pgrep -af` copied it into an agent transcript.
   - **The token leaves the launch env.** The daemon no longer puts `OPENRIG_ACTIVITY_HOOK_TOKEN` in a seat's launch environment.
     - Seats read the token from `<OPENRIG_HOME>/activity-endpoint.json` (mode 0600), which the daemon writes at startup.
     - Every reader already falls back to that file: the activity relay, the stub and Pi runners, `rig startup-proof`, and session transport's prerequisite check (which counts the file as the token).
   - **Self-attach** no longer returns the token in its response env. `rig attach --self --json` printed that response. It returns the daemon's `OPENRIG_HOME` instead, so a caller under a non-default home reads that daemon's endpoint file (review r2 I4 on #35).
   - **The guard.**
     - `createSession` and `respawnPane` refuse a launch env holding a secret-named variable, before any tmux command runs. Secret-named uses the `KEY|TOKEN|SECRET|PASSWORD|CRED|PASSPHRASE|PRIVATE` rule, case-insensitive.
     - The refusal is `secret_on_argv_refused`, naming the variable, never its value. A session refused at creation is never created. This applies in both modes.
     - One OpenRig name matches the rule but is not a secret: `OPENRIG_SEAT_ENV_KEYS`, whose value lists the seat's declared variable names. It is exempt by name, and only while its value has that shape (`NAME,NAME`); any other value is refused like any secret-named variable.
     - **A handover refuses before the cutover.** `respawnPane`'s refusal comes after the handover has ended the retiree, which would leave the seat dead (review r2 F1 on #35).
       - So the successor launcher checks the exact env it would pass to `respawnPane` before touching the pane, and refuses with `secret_on_argv_refused`, naming the variable.
       - The retiree keeps running. The guidance says to remove the variable and retry, never to relaunch, because a relaunch is refused the same way.
     - So a rig spec, or the provider-auth allow-list, that names a secret-named seat variable is refused at launch until the follow-up below.
   - **Not in this change (follow-up):** a channel that delivers a secret-named seat value without argv. The same follow-up covers the managed Claude launch, which forwards session variables by name onto `/usr/bin/env -i`'s argv (`"NAME=${NAME-}"`, so the value is on `env`'s argv while it runs). With the token gone from the launch env, nothing secret-named is forwarded that way unless a provider-auth name is configured, and a fresh launch with one is refused at `new-session`.
     - The verified candidate: `tmux source-file` of a 0600 file holding `set-environment` lines, removed after, then a pane restart.
     - On tmux 3.4, the pane sees the value, and no tmux process's argv holds it (only the file path is on argv).
   - **What this doesn't fix:** a server already started with the token keeps that argv until it exits. Rotating the token is the operator's decision.
10. Not changed:
   - Filter mode (byte-identical; the argv legacy-equivalence test drives every new site).
   - The daemon's own environment.
   - The managed launch's narrower `env -i` set.
   - Values that reach a seat through files (for example the on-disk signing key, which the seat-user plan covers).

## Requirements

- REQ-0013-01: While `seat_env.mode` is `filter`, the daemon shall launch seats exactly as spec 0006 does.
- REQ-0013-02: While `seat_env.mode` is `allowlist`, the daemon shall mark every inherited name a seat may not keep removed in that seat's tmux session on a fresh launch, a respawn and a native resume probe.
- REQ-0013-03: While `seat_env.mode` is `allowlist`, every command the daemon starts in a seat pane with `sendShellCommand` or `sendLaunchCommand` shall run only in an environment re-listed to hold no name the seat may not keep.
- REQ-0013-04: If a name matches the secret pattern, then the daemon shall not pass it to an allow-listed seat unless it is `OPENRIG_ACTIVITY_HOOK_TOKEN` or a named exception.
- REQ-0013-05: The daemon shall never pass `OP_SERVICE_ACCOUNT_TOKEN` or an `OP_SA_*` name to an allow-listed seat, whatever the base list, exceptions or launch names say.
- REQ-0013-06: While `seat_env.mode` is `allowlist`, the daemon shall set `KUBECONFIG` for a seat to the configured scoped file, or to a path that names no file while that file is absent.
- REQ-0013-07: If the allow-list cannot be applied to a launch, the environment cannot be listed, a name survives the scrub, or the policy cannot be read after anything but filter mode, then the daemon shall refuse that launch.
- REQ-0013-08: When the daemon drops names from an allow-listed seat, it shall log their count and the secret-named names, never a value.
- REQ-0013-09: The config stores shall refuse a secret-named base name, a pattern as an exception, a never-list name in the base list or exceptions, and a mode other than `filter` or `allowlist`.
- REQ-0013-10: If a tmux command fails, then the daemon shall report it without the command line or its output, so no launch value reaches a result, the database, an event or a log.
- REQ-0013-11: When the scrub refuses a launch, it shall name the step and the surviving names, never a value.
- REQ-0013-12: While `seat_env.mode` is `allowlist`, the daemon shall apply the allow-list to the names tmux's `update-environment` copies into a seat session.
- REQ-0013-13: While `seat_env.mode` is `allowlist`, a launch through `sendLaunchCommand` shall replace the staging shell once the scrub has run.
- REQ-0013-14: When the resume probe sees a shell in its pane's foreground before Claude's own process was seen there, the probe shall keep waiting rather than report the token not resumable.
- REQ-0013-15: If the resume probe's pane shows the scrub's refusal line while Claude is not the foreground process, then the probe shall report the token inconclusive.
- REQ-0013-16: The daemon shall not put the activity-hook token in a seat's launch environment.
- REQ-0013-17: If a launch environment passed to tmux holds a secret-named variable, then the tmux adapter shall refuse the launch before running any tmux command and name the variable without its value.
- REQ-0013-18: The self-attach response shall not include the activity-hook token.
- REQ-0013-19: When a seat's activity reader has no token in its environment, it shall read the token from the daemon's activity endpoint file.
- REQ-0013-20: If a handover successor's env holds a secret-named variable, then the successor launcher shall refuse the handover before ending the retiree.
- REQ-0013-21: The self-attach response shall include the daemon's `OPENRIG_HOME`.
- REQ-0013-22: While `seat_env.mode` is `allowlist`, if the scoped launch started a fresh pane, then `createSession` shall not restart that pane.

   - pilot one rig (`seat_env.rigs`);
   - name the exceptions;
   - relaunch the seats;

## Test

**Item 9** (`seat-env-no-secret-argv.test.ts`):
- **The sentinel test.** It starts a tmux server and a seat on a private socket the way the daemon does: the launch env comes from the daemon's own builder, with a sentinel token, and the adapter's command starts the server. It records every argv the adapter runs, then scans `/proc/*/cmdline` of every tmux process. The sentinel must appear in neither. Red first: before the change, the server's argv held it.
- **The guard:** a secret-named variable in `createSession`'s or `respawnPane`'s env is refused with `secret_on_argv_refused`, naming the variable. No tmux command runs, and the message carries no value.
- **Self-attach:** its response env holds no token, and names the daemon's `OPENRIG_HOME`.
- **The handover, real tmux:** a successor env with a secret-named seat variable (`TOKENIZERS_PARALLELISM`) is refused before the cutover. The retiree keeps its pid with `pane_dead 0`, and the cutover hook never fires; the control (`SAFE_SETTING`) respawns. The handover's guidance never names a relaunch.
- **The managed launch's `env -i` argv,** recorded deterministically with `sh -x`: no token and no secret-named value at head. With the base shape (the token in the launch env), the trace holds it.
- **The exemption's shape:** `OPENRIG_SEAT_ENV_KEYS` with a value that isn't a name list is refused.
- **The file fallback:** a seat whose env lacks the token resolves it from the endpoint file.
- **Break-once:** each rule, broken on purpose, turns its test red.

`seat-env-allowlist-tmux.test.ts` runs a private tmux server:
- its global environment carries placeholder operator names and an admin `KUBECONFIG`;
- its pane shell's startup file exports a secret-named name;
- it reads the pane shell's real environment and the names a launched command sees, in allow-list mode and in filter mode (the control, where those names still arrive).

With the prologue disabled on purpose, the allow-list case fails on the rc-exported name. It also covers the probe path (`sendLaunchCommand`) and a readonly export in the pane rc, which must stop the command.

It also checks, in allow-list mode with filter mode as the control:
- a `sendLaunchCommand` launch is the pane's foreground command (`pane_current_command`);
- the stub runtime's readiness check then reads ready, and the launched process keeps the guarantee (names only);
- the resume probe, with a stand-in `claude` on the pane's `PATH`, records the token resumable.

`resume-probe-launch-start.test.ts` scripts the probe's pane:
- a shell, then Claude, is resumable;
- a shell after the runtime was seen is not resumable;
- a shell that never leaves the foreground is inconclusive;
- the scrub's `awk` or `rm`, then a shell, is inconclusive, while `awk` then Claude is resumable;
- a refusal visible in the pane is inconclusive, even after `node` was seen;
- a resumed Claude whose history mentions the refusal, even at a line start, is resumable;
- the string elsewhere than at a line start is no refusal.

`seat-env-allowlist.test.ts` runs the generated prologue in a real `/bin/sh`, and in bash, zsh and dash:
- a readonly secret export stops the command with `seat_env_refused`, naming the step and the name;
- a removable one is removed and the command runs;
- with no awk on the pane's PATH the command does not run;
- a name such as `PAT*` is not glob-expanded against a file named `PATH` in the working directory, and the command keeps the shell's glob setting;
- in bash, exported `SHELLOPTS` and `BASHOPTS` don't stop the command;
- in bash, an exported function is removed, and one that cannot be unset (`readonly -f`) stops the command.

The real-tmux test also creates the seat from a client carrying `DISPLAY`, `KRB5CCNAME`, `SSH_CONNECTION` and `SSH_AUTH_SOCK`, which the server's global environment lacks. In allow-list mode the pane shell and the launched command keep only `SSH_AUTH_SOCK`; in filter mode, the control, the others arrive.

`refresh-probe-cleanup.test.ts` shows the resume-metadata probe staged behind the prologue in allow-list mode and typed as before in filter mode. Disabling the refusal, the staging or the fail-closed policy read turns these tests red.

`seat-env-secret-sentinel.test.ts` forces failed launches with a secret-named and an allowed sentinel value on the command line, and asserts neither appears in the result, any database row or the logs. With the redaction disabled on purpose, the `new-session` and respawn cases fail.
